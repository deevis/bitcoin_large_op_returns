CANONICAL ORDER OF OPERATIONS

Every confirmed protocol action X has the canonical position:

position(X) =
(
  blockHeight,
  blockTransactionIndex,
  protocolVout,
  recordOrdinal
)

Where:

blockHeight is the canonical confirmed block height.

blockTransactionIndex is the zero-based position of the transaction in the canonical full-node block transaction array.

protocolVout is the zero-based transaction output containing the protocol action.

recordOrdinal is the zero-based protocol-record position within that output and is zero when the output contains one record.

Positions are compared lexicographically from left to right.

Transaction identifiers identify transactions but do not determine their order.

Lexicographic, numeric, or timestamp sorting of txids is forbidden for confirmed state.

Mempool arrival time, displayed confirmation time, createdAt, database insertion order, and event identifiers do not determine confirmed protocol order.

The canonical block hash binds every position to the canonical chain.

A missing, duplicated, inconsistent, unavailable, or unverifiable canonical position fails closed.

The order of operations is:

1. confirmed block height;
2. transaction position inside that block;
3. protocol output position inside that transaction;
4. protocol record position inside that output;
5. the deterministic integer formulas defined below;
6. validation and freezing of the event result;
7. application of the event’s bond contribution.

Each valid action is completely calculated, validated, frozen, and applied before the next canonical position is evaluated.

For action X:

stateBefore(X) =
the state produced by replaying every valid confirmed action Y for which position(Y) is less than position(X).

stateAfter(X) =
apply(X, stateBefore(X)) when X is valid.

An invalid action causes no state mutation.

The next action uses the unchanged prior state.

SEQUENTIAL BLOCK REPLAY

There is no simultaneous confirmed protocol state.

Transactions that appear simultaneous to users are totally ordered by their confirmed canonical positions.

For confirmed block H, let its ordered Computer events be:

E1, E2, E3, ... Em

Let:

N(H,0) =
the final canonical liveNetworkValueQ8 from the end of block H - 1.

For each event Ek, in canonical order:

Nbefore(Ek) =
N(H,k-1)

First calculate and validate Ek using Nbefore(Ek).

If Ek is invalid:

N(H,k) =
N(H,k-1)

If Ek is valid:

1. freeze every economic and state result of Ek;
2. calculate canonicalBondContributionQ8(Ek);
3. calculate:

N(H,k) =
N(H,k-1) + canonicalBondContributionQ8(Ek)

The final network value of block H is:

Nend(H) =
N(H,m)

Nend(H) becomes the opening network value for block H + 1.

This replay rule applies identically whether one event or thousands of events confirm in the same block.

Each event is processed once.

An implementation may fetch, decode, and verify independent transaction data concurrently, but canonical state calculation and application must produce exactly the same result as the sequential replay defined here.

Partial block results are not canonical.

A block-derived state becomes canonical only after the entire block, its canonical block hash, every relevant transaction position, and every state transition have been verified.

If a block is detached from the canonical chain, its derived state is removed and the replacement canonical branch is replayed in the same deterministic order.

COMPUTE-THEN-BOND STATE TRANSITION

Every valid confirmed ProofOfWork Computer event is a bond event and may add to network value under the canonical network-value accounting rules.

For event X:

Nbefore(X) =
liveNetworkValueQ8(stateBefore(X))

The Computer first calculates and validates X using Nbefore(X).

If X is pending, invalid, unavailable, or unverifiable:

canonicalBondContributionQ8(X) = 0

Nafter(X) = Nbefore(X)

and X causes no canonical state or network-value mutation.

If X is valid, the Computer first freezes every economic result of X and then calculates:

Nafter(X) =
Nbefore(X) + canonicalBondContributionQ8(X)

An event’s own bond contribution is never included in its own calculation.

The valid contribution of X becomes available immediately after X and is included when evaluating every later canonical position, including later transactions in the same block.

Therefore:

1. a bond transaction ordered before a listing changes the value used by that listing;
2. a bond transaction ordered after a listing does not change or reprice that listing;
3. a valid listing adds its own bond contribution only after its terms are calculated and frozen;
4. the next listing sees the preceding valid listing’s contribution;
5. an invalid event contributes zero and does not affect later calculations.

Every proof payment, registry payment, miner fee, and other canonical network-value component is counted exactly once.

A proof output or fee must not be counted again merely because one transaction contains multiple protocol records.

A transaction-wide miner fee is applied exactly once after the final protocol record of that transaction. It becomes visible to later transactions and is never included in the calculation of an action within its own transaction.

A listing’s bond contribution includes only the proof value recognized for its confirmed listing transaction under the canonical network-value rules.

A future buyer payment is not counted as listing value before that purchase confirms. The purchase becomes its own later bond event.

CONFIRMATION-DERIVED UNIT FUNCTION

A pending pwt-sale-v5 listing commits one permitted USD face unit and authorizes this deterministic function.

A pending listing does not choose an arbitrary WORK amount or arbitrary proof price.

The canonical WORK amount and proof price do not exist until the listing confirms and receives its canonical position.

Let L be a confirmed listing.

Let:

F = unitFaceUsdCents

P = quoteBefore(L).usdPer100mProofsQ8

N = Nbefore(L)

S = 21000000

A = 100000000 atoms per WORK

Q = 100000000 network-value precision

R = 100000000 proofs

U = 100000000 USD quote precision

floorDiv(x, y) =
x / y using unsigned integer division

ceilDiv(x, y) =
(x + y - 1) / y using unsigned integer division

All values must be positive canonical unsigned integers.

Floating-point arithmetic is forbidden.

Every multiplication is completed before the indicated integer division.

Implementations must use integer arithmetic with sufficient precision and must fail closed on overflow.

Calculate:

targetNumerator =
F * R * U

targetDenominator =
100 * P

unitPriceSats =
ceilDiv(
  targetNumerator,
  targetDenominator
)

unitAmountAtoms =
floorDiv(
  targetNumerator * S * A * Q,
  targetDenominator * N
)

unitMinimumPriceSats =
ceilDiv(
  unitAmountAtoms * N,
  S * A * Q
)

A listing is valid only when:

1. F is in allowedFaceUsdCents;
2. quoteBefore(L) exists and is valid;
3. N is greater than zero;
4. unitPriceSats is greater than zero;
5. unitAmountAtoms is greater than zero;
6. unitMinimumPriceSats is greater than zero;
7. unitPriceSats is greater than or equal to unitMinimumPriceSats;
8. the seller has at least unitAmountAtoms of spendable WORK at stateBefore(L);
9. every existing seller, registry, signature, sale-ticket, and anchor rule is satisfied.

The proof payment rounds upward.

The WORK amount rounds downward.

The USD face unit remains fixed.

The amount of WORK represented by that face unit is determined by the exact network value immediately before the listing’s confirmed canonical position.

When an earlier valid event in the same block increases network value, every later listing in that block uses the increased value.

A listing does not contribute to its own unit calculation.

Its valid bond contribution becomes available only after its unit terms are calculated, validated, and frozen.

SEAL AND PURCHASE FINALITY

A confirmed valid listing remains eligible to be sealed and purchased at its immutable confirmation-derived terms.

A seal or purchase must:

1. reference the exact confirmed listing;
2. use authorization version pwt-sale-v5;
3. reproduce or reference the listing’s immutable derived terms;
4. transfer exactly unitAmountAtoms;
5. require exactly unitPriceSats as the unit sale price;
6. satisfy the existing ownership, signature, buyer, registry-payment, miner-fee, sale-ticket, anchor, and unspent-listing rules; and
7. appear after the listing in canonical order.

A seal or purchase must not recompute the listing’s WORK amount, USD price, USD quote, or network-value floor using the seal or purchase block.

The following events cannot invalidate an already-confirmed valid listing:

1. a later WORK network-value increase;
2. a later WORK network-value decrease;
3. a later bond;
4. a later transfer;
5. a later listing;
6. a later sale;
7. a later USD quote;
8. expiration of the listing’s original USD quote;
9. high traffic or the confirmation of any number of later events.

Network value and USD quote validity are admission rules for the listing at its confirmed canonical position.

They are not continuing conditions after the listing confirms.

A confirmed listing may close only through:

1. a valid seal and purchase;
2. a valid delisting;
3. expiration explicitly committed by the listing itself; or
4. the canonical spend of its sale-ticket outpoint under the existing outpoint rules.

A listing that was invalid when it confirmed is not resurrected by this declaration.
