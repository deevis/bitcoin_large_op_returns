Introduction\n==============================================================================\n\n\nMost non-financial data written to Bitcoin today is effectively opaque: raw\nhex, undocumented formats, one-off experiments and abandoned protocols. The\ndata is there forever, but in many cases it will be difficult or impossible to\ninterpret in ten or twenty years.\n\n\nBitcoin does not distinguish between \"financial\" and \"non-financial\" bytes;\nblocks contain whatever transactions miners accept, subject to consensus and\npolicy rules. Whether or not one likes non-transactional data on-chain, it\nalready exists and will continue to exist as long as it is economically\nviable.\n\n\nBitStory does not attempt to stop this. Instead, it offers a minimal,\nexplicit, and future-proof way to structure messages that are going to be\nwritten anyway:\n\n\n    * Clearly typed\n\n    * Signed and verifiable\n\n    * Self-describing (JSON)\n\n    * Easy to index\n\n\nIf the goal is \"this matters enough to be inscribed into Bitcoin\", BitStory\nensures that the inscription is not just a random blob, but a structured,\ncomprehensible record.\n\n\n==============================================================================\n2. Identity Key Generation (Dedicated BIP39 Seed)\n==============================================================================\n\n\nBitStory separates identity keys from payment keys. An identity key is used\nsolely for signing BitStory messages and must not control funds.\n\n\n------------------------------------------------------------------------------\n2.1 Rationale\n------------------------------------------------------------------------------\n\n\nReusing the same seed for both a Bitcoin wallet and a messaging identity is a\nserious security and privacy risk. BitStory enforces the separation\nconceptually:\n\n\n    * The identity seed and keypair are meant for signatures only.\n\n    * Payment (UTXO / wallet) keys belong in a separate wallet.\n\n    * If a BitStory identity is compromised, only the ability to sign new\n      messages is lost; no Bitcoin funds can be stolen.\n\n\n------------------------------------------------------------------------------\n2.2 Identity Key Process\n------------------------------------------------------------------------------\n\n\nBitStory does not mandate a specific derivation path or seed format in the\nwire protocol, but a typical client SHOULD:\n\n\n    * Generate a dedicated BIP39 seed (12-24 words) for BitStory.\n\n    * Derive a secp256k1 private key from this seed (e.g. at a fixed path\n      like `m/44'/0'/0'/0/0`, but this is implementation-dependent).\n\n    * Use this private key to sign all BitStory messages with a recoverable\n      ECDSA signature.\n\n    * Allow verifiers to reconstruct the compressed public key from the\n      signature alone.\n\n\nThe resulting public key is the cryptographic identity for that author in the\ncontext of BitStory.\n\n\n==============================================================================\n3. If the identity key is compromised, funds remain safe in a\nseparate wallet.\n\n\n==============================================================================\n4. PROFILE and PAGE Versioning\n==============================================================================\n\n\nBitStory supports updating PROFILE (PF) and PAGE (PG) messages by publishing\nnew versions. The blockchain's ordering (block height) determines which\nversion is considered canonical, while previous versions remain accessible.\n\n\n------------------------------------------------------------------------------\n7.1 PROFILE Updates (PF)\n------------------------------------------------------------------------------\n\n\n    * One public key = one active profile at any point in time.\n\n    * A profile is defined by a `(pubkey, \"PF\")` pair.\n\n    * When an author publishes a new PF message (same recovered pubkey, same\n      handle or a new handle), the latest PF by block height becomes the\n      canonical profile.\n\n    * Older PF messages remain part of the historical record.\n\n\nBehavior\n----------------------------------------\n\n\n    * Indexers should group PF messages by recovered pubkey.\n\n    * For each pubkey, the PF with the highest block height (and, if needed,\n      earliest txid within that block) is the active profile.\n\n    * History view: a client can offer a \"profile history\" tab showing all\n      past profiles for that pubkey.\n\n\n------------------------------------------------------------------------------\n7.2 PAGE Updates (PG)\n------------------------------------------------------------------------------\n\n\n    * A page is identified by the tuple `(pubkey, type=\"PG\", title=\"ti\")`.\n\n    * A single pubkey may have multiple pages, as long as each has a\n      different `ti`.\n\n    * To update a page, the author publishes a new PG message with the same\n      recovered pubkey, the same `ti` (page title), and updated `c` and/or\n      `su`.\n\n\nBehavior\n----------------------------------------\n\n\n    * Indexers should group PG messages by `(pubkey, ti)`.\n\n    * For each `(pubkey, ti)` pair, the PG with the highest block height is\n      the canonical version.\n\n    * Older versions are kept in history and can be surfaced on demand (e.g.\n      \"view previous versions\").\n\n\n------------------------------------------------------------------------------\n7.3 Version History\n------------------------------------------------------------------------------\n\n\nFor both PF and PG:\n\n\n    * All historical versions remain on-chain and verifiable.\n\n    * The canonical \"latest version\" is determined by ordering on-chain, not\n      by any field inside the JSON.\n\n    * A client can implement:\n\n        - \"current profile/page\" view (latest)\n\n        - \"version history\" view (all previous messages in that series)\n\n\n==============================================================================\n8. Replay, Duplication and Originality\n==============================================================================\n\n\nBitStory messages do not include timestamps in the signed payload; time is\nprovided by the Bitcoin blockchain (block height, block time, tx ordering).\nThis design has specific implications for replays.\n\n\n------------------------------------------------------------------------------\n10.1 What an Attacker Can and Cannot Do\n------------------------------------------------------------------------------\n\n\nCan Do\n----------------------------------------\n\n\n    * Copy an existing BitStory JSON message and its signature.\n\n    * Republish the exact same JSON + signature in a new transaction.\n\n\nCannot Do\n----------------------------------------\n\n\n    * Change the content (`c`, `ti`, etc.) without invalidating the signature.\n\n    * Change the author handle in a meaningful way: the recovered public key\n      still identifies the signer.\n\n    * Forge a new valid signature for a given message without the private key.\n\n\nA replay is therefore just a second inscription of the same statement by the\nsame key.\n\n\n------------------------------------------------------------------------------\n10.2 Defining the \"Original\"\n------------------------------------------------------------------------------\n\n\nIndexers may define a deterministic message identifier, for example:\n\n\nmessage_id = SHA256(canonical_json_without_s)\n\nFor each `message_id`, the original is:\n\n\n    * The instance with the lowest block height.\n\n    * If necessary, the earliest tx in that block.\n\n\nAny later transaction with the same `message_id` can be treated as a\nduplicate.\n\n\n------------------------------------------------------------------------------\n10.3 Behavior of the Protocol\n------------------------------------------------------------------------------\n\n\nFrom the protocol's perspective:\n\n\n    * Reposting the exact same message and signature does not create a new\n      profile, page, or post.\n\n    * It does not change the canonical version: the earliest on-chain\n      occurrence remains the \"original\".\n\n    * Duplicate inscriptions can be ignored or down-weighted by indexers.\n\n\nReplays are economically self-limiting: each replay costs additional fees\nwhile providing no new information.\n\n\n==============================================================================\n11. Economic Impact and Network Alignment\n==============================================================================\n\n\nBitStory does not attempt to make data storage on Bitcoin cheap. At\na fee rate of 2 sat/vByte:\n\n\n+--------------------+---------------+\n| Metric             | Value         |\n+====================+===============+\n| Payload size       | 1 kB          |\n| Transaction weight | ~1,141 vBytes |\n| Fee rate           | 2 sat/vByte   |\n| Estimated fee      | ~2,282 sats   |\n+--------------------+---------------+\n\n\nAt higher sizes (e.g. 10 kB), fees scale linearly. This is not a realistic attack vector compared\nto the effort required.\n\n\n------------------------------------------------------------------------------\n11.3 Contribution to Miner Incentives\n------------------------------------------------------------------------------\n\n\nAs block subsidies decline, security increasingly depends on fees. BitStory\ntransactions:\n\n\n    * Pay for blockspace.\n\n    * Do not pollute the UTXO set (data sits in OP_RETURN or witness, not in\n      fake outputs).\n\n    * Provide a fee-paying, opt-in use case for users who want permanent,\n      censorship-resistant publication.\n\n\nIn that sense, BitStory strengthens Bitcoin's fee market rather than\nundermining it.\n\n\n==============================================================================\n12.
